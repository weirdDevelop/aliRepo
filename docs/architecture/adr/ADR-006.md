# ADR-006: Permission keys + roles + scopes; pages map to keys

| Date | Status |
|---|---|
| 2026-11-04 | **Accepted** by owner 2026-11-04 |

## Context
Fixed role ENUM + page lists + org-role pages; record rules ad hoc. Task/approval features need finer, scoped permissions.

## Problem
RBAC with scopes and ABAC policies, without breaking current users (§10.2–10.5).

## Options considered
A) Extend page lists. B) Permission keys `context.resource.action` + roles + scoped grants + policy rules in services. C) External policy engine (OPA) — not runnable on shared hosting.

## Decision
B (see `permission-matrix.md`).

## Consequences
Role templates editable per tenant; migration generates roles equal to current grants (diff must be zero).

## Security impact
Default deny; SoD rules; viewer stays read-only by DB guard.

## Performance impact
Permission set cached per request (one query, as P-04 refresh already does).

## Migration impact
Generated roles from existing `permissions_json` and `eb_roles`.

## Rollback considerations
Old page checks remain valid during transition (keys `<page>.page.view`).

## Implementation note — 2.3.0 (2026-11-05)

Delivered in two phases to avoid two editors writing the same data:

* **Phase A (2.3.0):** the existing operator editor and org-chart editor remain the source of today's grants. `core/Permissions.php` projects them into keys (`<page>.page.view`, `*.page.view` for "all sections", `customer.person.delete`). Roles created in the new editor are **additive** grants on top. Proof of zero access change: a differential test (30,000 seeded grant combinations, >1M decisions) against a frozen copy of the pre-2.3.0 code, plus a live check of 40 synthetic users' page lists; both fail under a deliberate mutation.
* **Phase B (later):** materialise legacy grants as roles, retire `permissions_json` page lists and the old editor.
* Scopes: only `tenant` is accepted now; `org_unit`/`project` arrive with 2.4.0/2.5.0.
* Not converted yet (unchanged legacy behaviour): customer-group restriction, PII masking, supervisor/org-manager "sees all" flags.
