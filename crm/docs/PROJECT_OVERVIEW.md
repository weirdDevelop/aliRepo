## ۱) این پروژه چیه و چرا ساخته شده

**جاکجاست** (Jakojast.com) یک **OTA (آژانس مسافرتی آنلاین) و پلتفرم رزرو اقامتگاه** واقعی و فعال در ایران است — از نظر مدل کسب‌وکار، ترکیبی از Airbnb و Booking.com برای بازار ایران. برند «جاکجاست» متعلق به **شرکت کیمیای سبز حیات** است (دارای مجوز رسمی فعالیت).

**آمار و پوشش واقعی (طبق سایت رسمی):**
- پوشش **۳۱ استان و بیش از ۳۵۰ شهر و روستای ایران**
- بیش از **۴۴۹ میزبان فعال**
- پشتیبانی ۲۴ ساعته (تلفن، تلگرام: `t.me/JakojastHost`)
- دفتر مرکزی: تهران، هروی

**انواع اقامتگاه‌های ارائه‌شده (نمونه‌های واقعی سایت):**

| نوع | نمونه |
|---|---|
| آپارتمان مبله | آپارتمان دوخواب جاسمین - اشرفی اصفهانی، تهران |
| سوئیت | سوئیت‌های مبله کوتاه‌مدت |
| ویلا (با/بدون استخر) | ویلا دربست سه‌خواب کاکتوس - سوادکوه |
| کلبه | کلبه‌های طبیعت‌گردی |
| هتل‌آپارتمان | هتل آپارتمان یاس - صادقیه |
| اقامتگاه بوم‌گردی | آوای زندگی - تنکابن |
| تور گردشگری/کمپ | تورهای ایران‌گردی و کمپ در طبیعت |

جاکجاست همه‌ی فرآیند رزرو، پشتیبانی، و تسویه‌حساب با میزبان‌ها رو دیجیتالی و متمرکز می‌کنه: **بجای اینکه اطلاعات تماس‌ها، مشتری‌ها، میزبان‌ها، مرخصی پرسنل، حقوق، و تیکت‌های پشتیبانی پخش و پراکنده باشه، همه در یک سیستم واحد (همین CRM) ثبت و مدیریت می‌شه.**

## ۲) کسب‌وکار پشت این سیستم

**قوانین واقعی کسب‌وکار (طبق سؤالات متداول رسمی سایت) که مستقیماً روی طراحی این CRM اثر گذاشته:**

- **رزرو آنی:** مهمان بدون نیاز به تأیید میزبان، مستقیماً رزرو نهایی می‌کند.
- **واریزی به میزبان:** دقیقاً *بعد از خروج مهمان*، به شماره شبای اعلام‌شده توسط میزبان واریز می‌شود و **در صف واریزی قرار می‌گیرد** — این دقیقاً همان منطقی است که در ماژول «تسویه‌حساب میزبانان» (جدول `host_settlements`، وضعیت‌های `pending`/`paid`) در این CRM پیاده‌سازی شده.
- میزبانان **رایگان** ثبت‌نام می‌کنند و ملک خود را با تقویم و قیمت دلخواه ثبت می‌کنند.

جریان کاری واقعی که این سیستم پشتیبانی می‌کند:

```
مشتری زنگ می‌زند (از طریق تلفنچی)
        │
        ▼
جاکجاست تماس را همگام‌سازی می‌کند (خودکار یا دستی)
        │
        ▼
اگر شماره جدید بود → خودکار یا دستی تبدیل به «سرنخ» (Lead) می‌شود
        │
        ▼
اپراتور پشتیبانی بر اساس محل/بودجه‌ی درخواستی، اقامتگاه پیشنهاد می‌دهد
        │
        ▼
اگر رزرو نهایی شد (یا از طریق سایت با رزرو آنی) → مشتری وارد جدول
«مشتریان» (Customers) با تاریخچه‌ی کامل می‌شود
        │
        ▼
بعد از خروج مهمان → واریزی به میزبان در صف قرار می‌گیرد (Host Settlements)
```

موازی با این، بخش‌های داخلی سازمان هم مدیریت می‌شود: پرسنل، حضور و غیاب، مرخصی، حقوق و دستمزد، تیکت‌های پشتیبانی داخلی، تسک‌ها/پروژه‌ها، و چت داخلی تیم.

## ۳) معماری فنی

| بخش | فناوری |
|---|---|
| زبان بک‌اند | PHP خالص (بدون فریم‌ورک مثل Laravel/Symfony) |
| دیتابیس | MySQL/MariaDB |
| فرانت‌اند | HTML + CSS دستی + JavaScript خالص (بدون React/Vue) |
| ارتباط فرانت-بک | یک API داخلی REST-like (`api.php`) که JSON برمی‌گرداند |
| احراز هویت | توکن (Bearer Token) ذخیره‌شده در `auth_tokens` + `localStorage` سمت مرورگر |
| VoIP | تلفنچی (سرویس ابری تلفن ایرانی) - نگاه کنید به بخش ۷ |
| صدا به متن | Whisper (آفلاین، از طریق `b7s/whisper-php`) - نگاه کنید به بخش ۹ |
| پلیر صوتی | [Plyr](https://github.com/sampotts/plyr) (کتابخانه‌ی متن‌باز) |
| تقویم شمسی | پیاده‌سازی اختصاصی (بدون کتابخانه‌ی خارجی) در `assets/js/jalali-datepicker.js` |

**چرا بدون فریم‌ورک؟** این تصمیم از قبل از شروع همکاری ما با این پروژه گرفته شده بود (میراث کد). ساختار فایل‌ها یک الگوی MVC ساده و دستی را دنبال می‌کند:
- `models/` → منطق دیتابیس و قوانین کسب‌وکار (هر فایل = یک موجودیت مثل Customer، Lead، Call)
- `views/` → صفحات HTML+PHP که کاربر می‌بیند
- `core/` → کلاس‌های زیرساختی مشترک (Auth، Database، Logger، ...)
- `api.php` → یک فایل واحد و بزرگ که همه‌ی endpointهای API را روت می‌کند (نه فایل جدا به‌ازای هر route)

## ۵) دیتابیس - جدول‌ها و رابطه‌ها

| جدول | توضیح |
|---|---|
| `users` | حساب‌های ورود به سیستم (username/password/role/permissions) |
| `auth_tokens` | توکن‌های فعال ورود |
| `customers` | مشتریان نهایی (کسانی که رزرو انجام داده‌اند) |
| `customer_notes` | یادداشت‌های آزاد روی پروفایل مشتری |
| `hosts` | میزبانان (صاحبان ملک) |
| `host_settlements` | تسویه‌حساب‌های مالی با هر میزبان |
| `staff` | پرسنل داخلی سازمان (متصل به `users` از طریق `staff.user_id`) |
| `attendance` | حضور و غیاب (چند رکورد در روز مجاز - نگاه کنید به بخش ۱۱) |
| `staff_evaluations` | ارزیابی عملکرد پرسنل |
| `leaves` | درخواست‌های مرخصی (روزانه یا ساعتی) |
| `salaries` | فیش‌های حقوقی ماهانه |
| `calls` | **مرکز ثقل سیستم** - تمام تماس‌های همگام‌شده از تلفنچی |
| `telefonchy_events` | لاگ خام رویدادهای webhook دریافتی |
| `telefonchy_api_logs` | لاگ کامل هر تعامل با API تلفنچی (برای دیباگ) |
| `leads` | سرنخ‌های فروش (قبل از تبدیل به مشتری) |
| `host_leads` | سرنخ‌های جذب میزبان جدید |
| `tickets` | تیکت‌های پشتیبانی |
| `projects` / `tasks` | پروژه‌ها و تسک‌های داخلی تیم |
| `chat_messages` | چت داخلی تیم (کانال‌محور) |
| `settings` | تنظیمات کلید-مقدار سیستم (توکن تلفنچی، برند، ...) |

**رابطه‌ی کلیدی که باید بدونید:** جدول `calls` با سه جدول دیگر لینک می‌شود:
- `calls.contact_id` → `customers.id` (اگر شماره‌ی تماس متعلق به مشتری شناخته‌شده باشد)
- `calls.lead_id` → `leads.id` (اگر تماس به سرنخ تبدیل شده باشد)
- `calls.exten_number` → `staff.exten_number` (تطبیق با پرسنل بر اساس داخلی - **نه یک foreign key واقعی**، یک تطبیق رشته‌ای است)

## ۷) یکپارچه‌سازی با تلفنچی (VoIP)

📖 **مرجع کامل و همیشه‌به‌روز:** [`docs/TELEFONCHY_API.md`](TELEFONCHY_API.md) — این فایل جداگانه هر endpoint، فرمت دقیق پاسخ، و تاریخچه‌ی هر باگی که با آن مواجه شدیم را دارد. خلاصه‌ی حیاتی:

- **آدرس API:** `https://panel.telefonchy.com/webservice/v1`
- تماس‌ها هر ۵ دقیقه (یا دستی) با `CallSyncManager` همگام‌سازی می‌شوند
- رویدادهای بلادرنگ (زنگ خوردن/قطع شدن) از طریق `webhook.php` دریافت می‌شوند
- **نکته‌ی مهم:** پاسخ API تلفنچی یک لایه‌ی تودرتوی غیرمستند دارد (`response.data.data` نه `response.data.calls`) و حتی برای خطاها HTTP 200 برمی‌گرداند (خطای واقعی در `body.code` است) - این‌ها در کد و در مستند تلفنچی مفصل توضیح داده شده‌اند.

## ۸) سیستم دسترسی‌ها و کاربران

هر پرسنل می‌تواند یک حساب کاربری (`users`) داشته باشد که با `staff.user_id` به رکورد پرسنلی‌اش وصل است.

**نقش‌ها:**
- `admin` → دسترسی کامل و بدون محدودیت به همه‌چیز
- `manager` → می‌تواند تسک/پروژه بسازد؛ دسترسی‌های ماژولی طبق `permissions`
- `staff` → فقط دسترسی‌هایی که صراحتاً در `permissions` (ستون JSON روی `users`) فعال شده

**کلیدهای دسترسی موجود:** dashboard, customers, leads, hosts, host_leads, staff, leaves, payroll, tickets, chat, tasks, reports, calls, settings

**استثنای مهم:** صرف‌نظر از دسترسی ماژولی، هر کاربر همیشه به **پروفایل خودش** (اگر به یک پرسنل وصل باشد) دسترسی دارد - برای دیدن فیش حقوقی، ثبت مرخصی، و ورود/خروج خودش. لینک «🙋 پروفایل من» در منو این را نشان می‌دهد.

**محدودیت‌های نقشی دیگر:**
- فقط `admin`/`manager` می‌توانند تسک یا پروژه‌ی جدید بسازند
- فقط فرد مسئول یک تیکت یا `admin` می‌تواند آن را ببندد (⚠️ این چک بر اساس **تطابق نام** انجام می‌شود، نه شناسه - نقطه‌ضعف شناخته‌شده)

چهار روش پشتیبانی می‌شود (از تنظیمات قابل انتخاب):
- **local (Whisper):** رایگان، با [`b7s/whisper-php`](https://github.com/b7s/whisper-php) که Whisper.cpp را کاملاً روی سرور خودتان اجرا می‌کند - کیفیت متوسط. ⚠️ نیاز به کامپایل C++ دارد؛ روی سرورهایی با GCC قدیمی‌تر (مثلاً GCC 8 روی AlmaLinux 8) کامپایل با خطای `undefined reference to std::filesystem` شکست می‌خورد.
- **vosk (پیاده‌سازی‌شده و تست‌شده روی production):** رایگان، بدون هیچ کامپایلی - یک سرویس کوچک پایتون (Flask + پکیج آماده‌ی Vosk) که مدل فارسی را یک‌بار لود می‌کند و روی `127.0.0.1:8899` جواب می‌دهد. سبک‌تر و سریع‌تر از Whisper، برای تبدیل **فوری و خودکار بعد از هر تماس** مناسب است.
- **groq:** ابری، مدل واقعی Whisper large-v3، هزینه‌ی بسیار پایین (~$۰.۰۴ در ساعت صدا).
- **openai:** ابری، کیفیت مشابه Groq ولی ~۹ برابر گران‌تر.

⚠️ **پیش‌نیاز حیاتی برای Vosk:** تابع PHP به‌نام `exec()` باید فعال باشد (برای اجرای ffmpeg). روی هاست‌های DirectAdmin/CloudLinux معمولاً در `disable_functions` غیرفعال است - **در بیش از یک فایل هم‌زمان** (هم `php.ini` اصلی، هم فایل‌های override مثل `php.conf.d/50-webapps.ini`؛ هر دو باید ویرایش شوند). `TranscriptionService::isExecEnabled()` این را خودکار تشخیص می‌دهد و پیام واضح می‌دهد.

### تبدیل خودکار و «تقریباً لحظه‌ای»
تماس واقعاً real-time (هم‌زمان با خودِ مکالمه) ممکن نیست چون تلفنچی فایل ضبط را فقط **بعد از قطع تماس** می‌دهد. اما اگر روش فعلی `vosk` باشد، بلافاصله بعد از هر رویداد `hangup` که ضبط دارد (نه فقط دستی/کرون)، `CallSyncManager::ingestHangupEvent()` یک پردازش پس‌زمینه (`exec(...  &)`) برای همان تماس اجرا می‌کند - یعنی متن مکالمه معمولاً ظرف چند ثانیه بعد از پایان تماس آماده است. برای Whisper (سنگین‌تر) این کار عمداً انجام نمی‌شود - آن به صف دوره‌ای (`cron/transcribe_calls.php`، هر ۵ دقیقه، یا `--call_id=N` برای تست تکی) واگذار شده تا فشار هم‌زمان روی CPU زیاد نشود.

پردازش دستی (دکمه در جزئیات تماس) هم برای هر دو روش همیشه در دسترس است.

## ۹ب) پایش زنده‌ی تماس‌ها (Live Call Monitor)

از لحظه‌ای که تلفنچی رویداد «در حال زنگ خوردن» (ringing) را از طریق
webhook می‌فرستد:
1. تماس بلافاصله در دیتابیس ثبت می‌شود (وضعیت `ringing`)
2. اگر شماره متعلق به مشتری شناخته‌شده نباشد، **بلافاصله یک سرنخ ساخته می‌شود** (نه بعد از قطع تماس)
3. در صفحه‌ی تماس‌ها، پنل «🔴 پایش زنده تماس‌ها» هر ۵ ثانیه خودکار به‌روز می‌شود و تمام تماس‌های ۳۰ دقیقه‌ی اخیر را نشان می‌دهد
4. هر عضو تیم می‌تواند وضعیت پیگیری خودش را روی هر تماس ثبت کند (🆕 جدید / 👀 در حال رسیدگی / 📞 نیاز به تماس مجدد / ✅ حل شد) تا کل تیم هم‌زمان بداند چه کسی دارد به کدام تماس رسیدگی می‌کند

پیاده‌سازی: `Call::ensureLeadForRingingCall()`, `Call::updateLiveStatus()`, `Call::getLiveCalls()`, `GET /api/calls/live`, `PATCH /api/calls/{id}/live-status`

## ۱۱) باگ‌های بنیادی که پیدا و رفع شدند

این بخش برای این نوشته شده که **هیچ توسعه‌دهنده‌ی آینده دوباره این اشتباهات را تکرار نکند.**

### باگ ۱: تشخیص اشتباه id/action در کل `api.php`
نسخه‌ی اولیه فرض می‌کرد segments[2] همیشه «id» و segments[1] همیشه «اکشن» است. اما در عمل، همه‌ی URLهای واقعی پروژه به‌شکل `/resource/{id}/{subAction}` بودند - یعنی id در segments[1] است. نتیجه: **تقریباً تمام route های ویرایش/حذف/جزئیاتِ تک‌رکوردی در کل پروژه هیچ‌وقت کار نمی‌کردند** (ویرایش پرسنل، تبدیل تماس به سرنخ، اتصال داخلی، و ده‌ها مورد دیگر). در تمام ۱۲+ handler function رفع شد.

### باگ ۲: تداخل پارامتر `page` در صفحه‌بندی
روتر اصلی (`index.php`) از `?page=customers` برای «کدام صفحه» استفاده می‌کند. همزمان، تمام ۹ صفحه‌ی لیست (مشتریان، سرنخ‌ها، ...) از **همان اسم پارامتر** برای «شماره صفحه» استفاده می‌کردند. چون یک کلید URL نمی‌تواند دو مقدار داشته باشد، کلیک روی «صفحه ۲» کل روتر را گم می‌کرد. رفع شد: شماره صفحه الان `p=` است.

### باگ ۳: تلفنچی - تشخیص موفقیت/خطا بر اساس کد HTTP اشتباه
تلفنچی حتی برای خطاهای واقعی (Validation Error) هدر HTTP را `200 OK` برمی‌گرداند؛ خطای واقعی فقط در بدنه‌ی JSON (`code`) است. رفع شد.

### باگ ۴: لیست اپراتورها و محلات کاملاً ساختگی بود
`Lead::getOperators()` یک لیست ثابت از ۴ نام نمونه برمی‌گرداند که هیچ ربطی به پرسنل واقعی نداشت. الان از جدول `staff` (فقط واحد پشتیبانی) خوانده می‌شود. مشابه برای لیست محلات.

### باگ ۵: محدودیت «یک رکورد حضور در روز»
جدول `attendance` یک `UNIQUE KEY(staff_id, date)` داشت که اجازه‌ی بیش از یک ورود/خروج در روز را نمی‌داد. حذف شد؛ الان هر «ورود» یک نوبت جدید می‌سازد.

### باگ ۶: جستجوی سراسری هیچ‌وقت وصل نبود
باکس جستجوی بالای صفحه از ابتدا فاقد هرگونه کد جاوااسکریپت بود.

### باگ ۷: وب‌هوک تلفنچی هیچ‌وقت `ringing`/`hangup` را تشخیص نمی‌داد
کد فرض می‌کرد payload وب‌هوک زیر یک کلید `data` تودرتوست (`$payload['data']`). با دیدن نمونه‌ی خام واقعی (پنل «🔬 دریافتی خام webhook»)، مشخص شد **هیچ کلید `data` در ریشه وجود ندارد** - همه‌چیز مستقیم در ریشه است. نتیجه: تمام ۱۰۳۰+ رویداد واقعی به‌عنوان `(unknown)` ثبت می‌شدند و هیچ‌وقت تماس/سرنخی از webhook ساخته نمی‌شد (فقط با کلیک دستی دکمه‌ی sync کار می‌کرد). رفع شد در `webhook.php`.

### باگ ۸: ساختار `ringing` و `hangup` کاملاً متفاوتند (نه فقط یک نام رویداد)
- `ringing`: مقصد کلیدش `dest` است؛ شماره‌ها به‌صورت **عدد JSON** می‌آیند (نه رشته) - یعنی صفر ابتدایی موبایل ایرانی گم می‌شود چون JSON عدد نمی‌تواند صفر ابتدایی داشته باشد. رفع شد با `normalizeIranianMobile()`.
- `hangup`: مقصد کلیدش `dst` است (نه `dest`!)؛ وضعیت در `disposition` است (نه `status`)؛ `duration`/`billsec`/`wait`/`record` مستقیم در خودِ payload هستند (نیازی به enrichment جدا نیست)؛ `starttime`/`endtime` به وقت **UTC** هستند (نه محلی، برخلاف `ringing` که `datetime` را مستقیم به وقت تهران می‌دهد).

### باگ ۹: هر تماس خروجی، یک «لگ تکراری و خراب» هم دارد
تلفنچی برای هر تماس خروجی واقعی، **دو** رویداد `hangup` با cuid متفاوت می‌فرستد: یکی تمیز (از داخلی واقعی)، و یکی از یک اپ داخلی خودشان با `src` ثابت و `dst`/`did` به‌هم‌چسبیده و بی‌معنی (مثلاً `98219109459909364453659`). سیگنال تشخیص قطعی: لگِ خراب همیشه هم `entry_point` هم `outgoing_point` را با هم دارد؛ لگِ تمیز فقط `outgoing_point`. رفع شد با `isDuplicateOutgoingAppLeg()` - این لگ‌ها کاملاً نادیده گرفته می‌شوند.

### باگ ۱۰: شبکه‌ی ایمنیِ تبدیل خودکار تماس به سرنخ عملاً هیچ‌وقت اجرا نمی‌شد
`autoGenerateLeadsFromRecentCalls()` (که تماس‌های بدون سرنخ را جارو می‌کند) فقط وقتی `$newCount > 0` در همان اجرای sync بود صدا زده می‌شد. اما چون وب‌هوک همیشه زودتر از cron دوره‌ای تماس را ثبت می‌کند، `$newCount` تقریباً همیشه صفر بود. رفع شد: این تابع حالا در هر اجرای sync بدون قید صدا زده می‌شود.

### باگ ۱۱: `GET /call?call_id=...` (تک‌تماسی) همیشه ۵۰۰ برمی‌گرداند
نه گاه‌به‌گاه - **۱۰۰٪ از موارد**، طبق لاگ‌های واقعی چند روزه. این یعنی `file_id` (لازم برای پخش صدا و تبدیل به متن) هیچ‌وقت از این مسیر پر نمی‌شد. رفع شد: به‌جای این endpoint، یک جست‌وجوی باریک (۱۰ دقیقه‌ای) در همان `GET /calls` (لیست) که همیشه کار می‌کند انجام می‌شود (`enrichCallViaListLookup()`).

### باگ ۱۲: لیست سفید (whitelist) تنظیمات، کلیدهای تبدیل صدا به متن را نداشت
`PUT /api/settings` یک آرایه‌ی `$allowed` دارد؛ کلیدهای `transcription_provider`, `vosk_worker_url`, `groq_api_key`, `openai_api_key` هیچ‌وقت در آن نبودند. نتیجه: ذخیره‌ی این تنظیمات همیشه پیام «موفق» می‌داد ولی **هیچی واقعاً ذخیره نمی‌شد**. رفع شد. ⚠️ **درس برای آینده:** هر کلید تنظیمات جدید باید همان‌جا هم اضافه شود.

### باگ ۱۳: `exec()` روی سرور در **دو فایل هم‌زمان** غیرفعال بود
روی این سرور خاص (DirectAdmin + OpenLiteSpeed + AlmaLinux 8)، `disable_functions` هم در `php.ini` اصلی هم در `php.conf.d/50-webapps.ini` جداگانه ست شده بود - ویرایش فقط یکی کافی نبود. علاوه بر این، حتی بعد از ویرایش هر دو و ری‌استارت کامل وب‌سرور، یک پردازش `lsphp` **یتیم و ۶ روزه** هنوز زنده بود و تنظیمات قدیمی را در حافظه نگه داشته بود؛ فقط با `kill -9` روی همان PID مشکل حل شد. **درس مهم:** بعد از هر تغییر php.ini روی OpenLiteSpeed، `ps -eo pid,lstart,cmd | grep lsphp` را چک کنید تا پردازش یتیم قدیمی نمانده باشد.

## ۱۱ب) `call_category` و پایپ‌لاین سرنخ میهمان (نسخه‌ی ۲)

- **`calls.call_category`**: `guest`/`host`/`recruitment`/`spam`/`internal`/`unclassified`. تشخیص خودکار فقط برای `internal` (نوع تماس) و `host` (تطبیق با جدول `hosts`) قابل‌اطمینان است؛ بقیه دستی‌اند. یک انتخاب دستی هیچ‌وقت توسط منطق خودکار بازنویسی نمی‌شود (`CallSyncManager::attemptContactAndLeadLinking()`).
- **پایپ‌لاین سرنخ میهمان** از ۶ وضعیت کلی به ۹ مرحله‌ی واقعی رزرو تغییر کرد: `جدید → تماس گرفته شد → اقامتگاه پیشنهاد شد → در انتظار تأیید میزبان → پیش‌فاکتور ارسال شد → در انتظار پرداخت → رزرو نهایی شد` + `منصرف شد`/`بی‌پاسخ`. تاریخچه‌ی هر تغییر وضعیت در جدول `lead_status_history` ثبت می‌شود (`Lead::logStatusChange()`, `Lead::getStatusHistory()`).
- **`lead_references`**: جدول واقعی جایگزین لیست ثابت قدیمیِ «مرجع» شد؛ از تنظیمات قابل مدیریت است (`models/Reference.php`).
- **اپراتورهای آنلاین**: `users.last_activity` با هر درخواست موفق API آپدیت می‌شود (throttle شده، هر ۳۰ ثانیه)؛ `User::getOnlineStatus()` آستانه‌ی آنلاین بودن را ۳ دقیقه‌ی اخیر در نظر می‌گیرد. پنل زنده در `staff.php`.

## ۱۳) وضعیت فعلی

### ✅ کامل، تست‌شده روی سرور واقعی
- **یکپارچه‌سازی تلفنچی (کاملاً رفع‌شده):** وب‌هوک `ringing`/`hangup` با ساختار واقعی (نه فرضی) پردازش می‌شود؛ تبدیل خودکار تماس ورودی/خروجیِ ناشناس به سرنخ (لحظه‌ی زنگ خوردن + fallback بعد از hangup + شبکه‌ی ایمنی دوره‌ای)؛ فیلتر لگ‌های تکراری/خراب تماس خروجی؛ پخش صدا و `file_id` از مسیر لیست قابل‌اعتماد (نه endpoint همیشه-خراب تک‌تماسی).
- **پنل «🔬 دریافتی خام webhook»**: مشاهده‌ی مستقیم payload خام تلفنچی از پنل، بدون نیاز به SSH/دیتابیس.
- **تبدیل صدا به متن**: چهار روش (Whisper محلی/Vosk محلی/Groq/OpenAI)؛ Vosk تست‌شده و کار می‌کند روی production، شامل تبدیل خودکار «تقریباً فوری» بعد از هر تماس ضبط‌شده.
- **پایپ‌لاین سرنخ میهمان (۹ مرحله)** + `call_category` (طبقه‌بندی مهمان/میزبان/جذب‌نیرو/اسپم/داخلی) + تاریخچه‌ی تغییر وضعیت.
- **مدیریت مراجع سرنخ** (جدول واقعی، نه لیست ثابت) + **اپراتورهای آنلاین** (وضعیت حضور لحظه‌ای بر اساس فعالیت واقعی API).
- ستون «آخرین به‌روزرسانی» + مرتب‌سازی در لیست سرنخ‌ها؛ لینک‌شدن باکس‌های KPI تماس‌ها به فیلتر؛ لینک‌شدن اسم مخاطب/سرنخ در لیست تماس‌ها به پروفایل؛ فرم اپراتور جدید کامل (داخلی/ایمیل/وضعیت)؛ تیک ✅ برای سرنخ‌های تبدیل‌شده به رزرو.
- پایش زنده‌ی تماس‌ها، داشبورد تماس‌ها، اتصال داخلی↔پرسنل، پلیر صوتی، RBAC، تولید خودکار کاربر برای پرسنل، رفع باگ‌های بنیادی id/action و صفحه‌بندی، چت (تا حد رفع‌شده)، جستجوی سراسری، تقویم شمسی، فیلتر اپراتور، سرچ/افزودن محل، مانده‌ی میزبانان، مرخصی ساعتی، دسترسی شخصی پروفایل، محدودیت ساخت تسک و بستن تیکت.

### 🟡 نیمه‌کاره یا نیازمند اطلاعات بیشتر برای ادامه
لیست ۱۹موردیِ کارفرما (بخش «برای برنامه‌نویس») - موارد باقی‌مانده که نیاز به دسترسی/تصمیم دارند:
- اتصال به دیتابیس سایت اصلی جاکجاست (روی همین سرور، قابل‌دسترسی طبق تأیید کارفرما) برای: مشتریان سایت (#۸)، فیلدهای سبک «یاس مبله» برای مشتریان (#۹)، میزبانان سایت + اقامتگاه‌هاشون (#۱۰، #۱۱، #۱۲)، استعلام‌های سایت به‌عنوان سرنخ (#۱۳)، گزارش‌های سیستم قدیم (#۱۵)، لیست فروش سایت (#۱۶).
- پیامک خودکار برای تماس بی‌پاسخ (#۱۴) - نیاز به انتخاب سرویس پیامک.
- گزارش‌های ساعتی/روزانه/هفتگی اپراتور (#۱۹) - نیاز به توافق روی معیارهای دقیق.
- اسکرپرهای رزرو/قیمت رقبا (#۱۷، #۱۸) - پروژه‌ی جدا، نیاز به بحث فنی/حقوقی مجزا.

## ۱۴) تصمیمات مهندسی و چرایی‌شون

- **چرا Whisper به‌جای یک API ابری؟** درخواست صریح کارفرما برای راه‌حل رایگان و آفلاین؛ چون سرور اختصاصی (نه هاست اشتراکی) در اختیار دارند، این ممکن شد.
- **چرا لاگ‌گیری اختصاصی تلفنچی به‌جای فقط لاگ فایل سرور؟** چون کارفرما به فایل‌سیستم سرور دسترسی مستقیم نداشت و برای عیب‌یابی، مشاهده‌ی لاگ از داخل پنل ضروری بود.
- **چرا فایل‌های تغییریافته جدا ارسال می‌شوند نه کل zip؟** درخواست اولیه‌ی کارفرما برای سهولت جایگزینی روی سرور شلوغ production؛ بعداً به درخواست خودش به «زیپ فقط شامل فایل‌های تغییریافته‌ی هر مرحله، با ساختار پوشه‌ی حفظ‌شده» تغییر کرد (نامگذاری: `jakojast-update-vN-PARTIAL.zip`).
- **چرا PHP خالص بدون فریم‌ورک برای اسکرپر پیشنهادی؟** کارفرما تسلط به پایتون ندارد و هاستش امکان اجرای پایتون را نمی‌دهد.
