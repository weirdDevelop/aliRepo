# مستند مرجع یکپارچه‌سازی تلفنچی (جاکجاست CRM)

> ⚠️ **این فایل باید با هر تغییری در `api_integration/TelefonchyAPI.php`،
> `api_integration/CallSyncManager.php` یا `webhook.php` هم‌زمان به‌روزرسانی شود.**
> هدف این است که همیشه یک منبع واحد و قابل‌اعتماد از «چه چیزی الان تأیید
> شده و از کجا» وجود داشته باشد، به‌جای این‌که دوباره از صفر مستندات
> تلفنچی جست‌وجو شود.

آخرین به‌روزرسانی: مطابق مستندات رسمی که کاربر مستقیماً از پنل راهنمای
تلفنچی (help center، تاریخ سند ۲۰ اردیبهشت ۱۴۰۵) کپی و ارسال کرده است.

---

## ۰) اطلاعات پایه اتصال

| مورد | مقدار |
|---|---|
| Base URL | `https://panel.telefonchy.com/webservice/v1` |
| احراز هویت | هدر `webservice-token: {TOKEN}` (توکن از پنل کاربری تلفنچی) |
| فرمت پاسخ استاندارد | `{status, code, message, data, paginator?}` |
| `status: "Ok"` و `code: 200` | یعنی موفق |

⚠️ **باگ حیاتی کشف‌شده (مهم برای هر endpoint، نه فقط calls):** تلفنچی
حتی برای خطاهای واقعی (مثل `Validation-Error`, کد ۴۰۰) هدر انتقال HTTP
را `200 OK` برمی‌گرداند! تشخیص موفقیت/خطا **هرگز** نباید بر اساس کد
HTTP transport باشد؛ همیشه باید `decoded.status === "Ok" && decoded.code === 200`
از داخل بدنه‌ی JSON چک شود. این دقیقاً همان چیزی بود که با curl دستی
کشف شد (`HTTP/1.1 200 OK` ولی بدنه `{"code":400,"status":"Validation-Error"}`).

⚠️ **تاریخچه‌ی تغییر دامنه (برای جلوگیری از سردرگمی آینده):**
1. ابتدا در کد قدیمی: `https://api.telefonchy.com` ← **اشتباه، اصلاً وجود نداشت**
2. سپس بر اساس مستندات عمومی/قدیمی گیت‌هاب: `https://telefonchy.com/webservice/v1` ← قدیمی بوده
3. **فعلی و تأیید شده:** `https://panel.telefonchy.com/webservice/v1`

این مقدار در `config.php` به‌صورت `TELEFONCHY_BASE_URL` تعریف شده و در
تنظیمات پنل هم قابل override است (جدول `settings`، کلید `telefonchy_base_url`).

## ۲) دریافت لیست تماس‌ها (فهرست، با فیلتر)

```
GET /calls?service_id=...&date_from=...&date_to=...&type=...&status=...
    &call_source=...&call_dest=...&exten=...&trunk_id=...&note=...
    &sort=DESC&page=1
Header: webservice-token
```

**فیلترهای پشتیبانی‌شده (همه اختیاری جز service_id):**

| پارامتر | نوع | توضیح |
|---|---|---|
| `service_id` | string | **اجباری** |
| `date_from` / `date_to` | string شمسی | فرمت `Y/m/d H:i` (مثلاً `1405/05/27 00:00`) |
| `type` | string | `incoming` \| `outgoing` |
| `status` | string | نمونه دیده‌شده: `ANSWERED`؛ مستندات فیلتر ورودی را `awnser`(تایپو)/`no-answer` هم ذکر کرده |
| `call_source` / `call_dest` | string | شماره |
| `exten` | string | شماره داخلی |
| `trunk_id` | string | شناسه ترانک |
| `note` | string | یادداشت تماس |
| `sort` | string | **باید دقیقاً یکی از این ۴ مقدار باشد:** `created_at DESC`, `created_at ASC`, `time_talk DESC`, `time_talk ASC` (نه فقط `ASC`/`DESC` تنها - این نکته با curl دستی کشف شد؛ مقدار اشتباه باعث `Validation-Error` می‌شود، پیش‌فرض `created_at DESC`) |
| `page` | int | پیش‌فرض `1` |

**⚠️ نکته‌ی حیاتی (باگ واقعی که رخ داد و رفع شد):**
وقتی هیچ تماسی در بازه‌ی درخواستی نیست، تلفنچی **`"data": null`** برمی‌گرداند
(نه آرایه‌ی خالی `[]`). کد قبلی از `$decoded['data'] ?? $decoded` استفاده
می‌کرد که در PHP، `null` را با «کلید data وجود ندارد» یکی می‌گیرد و در
نتیجه کل پاسخ (شامل `status`, `code`, `message`) به‌جای لیست تماس‌ها
پردازش می‌شد → `TypeError` روی هر آیتم (چون `status` رشته، `code` عدد،
`message` می‌شد `null` است، نه آرایه). **رفع شد** با
`array_key_exists('data', $decoded) ? $decoded['data'] : $decoded` در
`TelefonchyAPI::request()` + یک لایه‌ی محافظتی اضافه در
`CallSyncManager::runSync()` که هر آیتم غیر-آرایه را قبل از پردازش فیلتر
می‌کند.

**⚠️ نکته‌ی حیاتی‌تر و جدیدتر (کشف‌شده با curl دستی - این یکی هیچ‌جا،
حتی در مستندات رسمی، نوشته نشده بود):** ساختار واقعی پاسخ یک لایه‌ی
تودرتوی اضافه دارد:
```json
{
  "status": "Ok", "code": 200, "message": null,
  "data": {
    "status": "success",
    "data": [ { "cuid": "...", "call_source": "...", ... }, ... ],
    "pagination": {
      "current_page": 1, "total_pages": 16, "total_items": 380,
      "items_per_page": 25, "has_more": true, "total_is_exact": true
    },
    "date_default_from": {"date": "1405/06/03", "time": "00:00"},
    "date_default_to":   {"date": "1405/06/03", "time": "23:59"},
    "trunks": [], "extens": []
  }
}
```
یعنی لیست واقعی تماس‌ها در **`response.data.data`** است (نه
`response.data.calls`)، و اطلاعات صفحه‌بندی در **`response.data.pagination`**
است (نه `response.paginator`). این دقیقاً همان چیزی بود که باعث می‌شد
sync هیچ خطایی ندهد ولی همیشه صفر تماس ذخیره کند.

**نکته‌ی جانبی مهم:** اگر `date_from`/`date_to` اصلاً فرستاده نشود،
تلفنچی پیش‌فرض را روی **فقط همان روز** می‌گذارد (مطابق
`date_default_from`/`date_default_to` در پاسخ). برای گرفتن کل تاریخچه
باید صریحاً یک `date_from` قدیمی فرستاد.

**ساختار هر تماس در `data.data[]`:**

| فیلد | نوع | توضیح |
|---|---|---|
| `cuid` | string | شناسه‌ی یکتای تماس (کلید اصلی که در دیتابیس محلی هم همین است) |
| `server_id` | string | شناسه سرور |
| `call_source` / `call_dest` | string | شماره‌ها (رشته‌ی ساده - **نه** آبجکت) |
| `type` | string | `incoming` \| `outgoing` (نسخه‌های قدیمی‌تر `local` هم داشتند) |
| `status` | string | مثلاً `ANSWERED` |
| `time_wait` / `time_talk` | int (ثانیه) | |
| `started_at` / `ended_at` | string میلادی | |
| `jalali_started_at` / `jalali_ended_at` | string شمسی | تلفنچی خودش تبدیل می‌کند - نیازی به تبدیل دستی نیست |
| `trunk` / `trunk_id` | string | |
| `exten.number` / `exten.name` | آبجکت | داخلی مرتبط |
| `contact.call_source` / `contact.call_dest` | آبجکت | اطلاعات مخاطب (type/contact_id/name) - فعلاً استفاده نمی‌شود |
| `file_record` | string\|null | نام فایل ضبط؛ `null` یعنی تماس ضبط نشده |
| `file_id` | string\|null | شناسه‌ی لازم برای دانلود صدا (بخش ۴) |
| `id` | string | شناسه‌ی دیگر (مانگو-محور، استفاده نمی‌شود) |

پیاده‌سازی: `TelefonchyAPI::getCalls($filters)`, پردازش در
`CallSyncManager::processCall()`

## ۳) دریافت اطلاعات یک تماس مشخص

```
GET /call?call_id={cuid}
Header: webservice-token
```

⚠️ **نکته‌ی گمراه‌کننده:** پارامتر اسمش `call_id` است ولی مقداری که باید
داخلش گذاشت همان **`cuid`** تماس است. مسیر هم **مفرد** است: `/call` (نه `/calls`).

**پاسخ (`data` یک آرایه با یک عضو است):**

| فیلد | توضیح |
|---|---|
| `object_id`, `node` | داخلی دیتابیس تلفنچی |
| `record_id`, `file_id`, `file_saved` | اطلاعات ضبط (`file_saved: "0"` یعنی ضبط نشده) |
| `cuid`, `type`, `trunk`, `status`, `note` | مشابه بخش ۲ |
| `call_source`, `call_dest`, `call_number` | شماره‌ها |
| `time_wait`, `time_talk` | ثانیه |
| `created_at`, `updated_at`, `ended_at` | میلادی؛ **بدون** فیلد jalali |

**کاربرد اصلی در این پروژه:** بعد از دریافت رویداد `hangup` در وب‌هوک
(بخش ۵)، بلافاصله این endpoint صدا زده می‌شود تا جزئیات کامل (status
نهایی، مدت مکالمه، file_id) enrich شود، چون خودِ payload وب‌هوک این‌ها را ندارد.

پیاده‌سازی: `TelefonchyAPI::getCallInfo($cuid)`,
`CallSyncManager::ingestHangupEvent()`

## ۴) دریافت صوت مکالمه (دانلود ضبط تماس)

```
GET /calls/record?file_id={FILE_ID}&cuid={CUID}
Header: webservice-token
```

هر دو پارامتر **اجباری** هستند (فقط `file_id` کافی نیست). پاسخ، محتوای
باینری فایل (معمولاً MP3) است، نه JSON.

پیش‌نیاز: باید قبلاً از طریق GET `/calls` یا GET `/call`، مقادیر
`file_id` و `cuid` تماس را داشته باشیم. اگر `file_record` تماس در
دیتابیس محلی `null` باشد، یعنی اصلاً ضبط نشده و درخواست این endpoint
بی‌فایده است.

پیاده‌سازی: `TelefonchyAPI::downloadRecording($fileId, $cuid)`,
مصرف‌شده در `api.php` → `GET /api/play-recording?id={callId}`

**ستون دیتابیس محلی:** جدول `calls` یک ستون `file_id` دارد (اضافه‌شده
خودکار توسط `Call::ensureFileIdColumn()` در صورت نبود، بدون نیاز به
migration دستی).

## ۵) دریافت ایونت تماس (Webhook بلادرنگ)

آدرس وب‌هوک در پنل تلفنچی ثبت می‌شود: `https://your-domain.com/webhook.php`

📌 **آدرس واقعی این نصب (جاکجاست روی ساب‌فولدر `/crm/`):**
```
https://jakojast.com/crm/webhook.php
```
این آدرس دقیقاً همینی است که باید در پنل تلفنچی، بخش تنظیم وب‌هوک رویداد
تماس (events_hook) ثبت شود.

دو نوع رویداد با `POST` به این آدرس ارسال می‌شود:

| رویداد | زمان ارسال | جزئیات موجود در payload |
|---|---|---|
| `ringing` | قبل از پاسخ دادن | فقط شماره‌ها و نوع تماس (نه status نهایی) |
| `hangup` | بعد از قطع تماس | باز هم status/مدت/فایل صوتی **نیست** - باید با بخش ۳ enrich شود |

**ساختار کامل payload:**
```json
{
  "uid": "...", "rid": "...", "message": "request sent",
  "data": {
    "service_id": "...",
    "cuid": "173133386.125769",
    "unique_id": "173133386.125769",
    "src": "89**3", "dest": "912****975",
    "type": "outgoing",
    "event": "ringing",
    "datetime": "2024-11-18 16:55:37",
    "trunk_number": "021******75",
    "trunk_outgoing": "pishgaman",
    "webservice_token": "...",
    "events_hook": "your_url",
    "app_name": "parsvt",
    "date": "2024-11-18 16:55:38"
  },
  "created_at": "2024-11-18 16:55:38",
  "type": "info"
}
```

⚠️ **نکات مهم پیاده‌سازی:**
- اطلاعات اصلی داخل کلید `data` است، نه در ریشه‌ی payload.
- شماره‌ها (`src`/`dest`) نه `call_source`/`call_dest`.
- امنیت: مقدار `data.webservice_token` باید با توکن ذخیره‌شده‌ی ما یکی
  باشد؛ در `webhook.php` این چک انجام می‌شود و در صورت عدم تطابق، `403`
  برگردانده می‌شود (برای جلوگیری از تماس قلابی جعلی).
- طبق مستندات، سرور باید **سریع** ۲۰۰ برگرداند. چون این پروژه صف
  (queue) ندارد، فراخوانی enrich (بخش ۳) به‌صورت synchronous انجام
  می‌شود؛ اگر حجم تماس‌ها خیلی بالا رفت، باید به یک صف واقعی (مثل
  دیتابیس-محور یا Redis) منتقل شود تا timeout رخ ندهد.

پیاده‌سازی: `webhook.php`, `CallSyncManager::ingestRingingEvent()`,
`CallSyncManager::ingestHangupEvent()`

## سیستم لاگ‌گیری (`telefonchy_api_logs`)

هر تعامل با تلفنچی (چه ما درخواست بزنیم، چه وب‌هوک از آن‌ها برسد) در
جدول `telefonchy_api_logs` ثبت می‌شود (مدل: `models/TelefonchyApiLog.php`).
این جدول خودش در اولین استفاده ساخته می‌شود (نیازی به SQL دستی نیست).
از پنل تنظیمات → «📋 لاگ تعاملات با تلفنچی» قابل مشاهده و پاک‌کردن است.

همچنین، از نسخه‌ی فعلی، **خطاهای داخلی PHP** (نه فقط خطاهای شبکه) هم در
همین جدول ثبت می‌شوند (`api.php` کچ کلی + `CallSyncManager` کچ به‌ازای
هر تماس) تا در صورت بروز باگ، بدون نیاز به دسترسی به فایل لاگ سرور،
مستقیماً از پنل قابل دیدن باشد.

| نسخه ۸ | **علت اصلی «۲۰۰ موفق ولی data:null» با curl دستی پیدا شد:** ۱) پارامتر `sort` باید دقیقاً یکی از `'created_at DESC'`, `'created_at ASC'`, `'time_talk DESC'`, `'time_talk ASC'` باشد - نه فقط `DESC`/`ASC` (مستندات اشتباه نوشته بودند). با مقدار اشتباه، تلفنچی خطای `Validation-Error` (code:400) برمی‌گرداند. ۲) **باگ حیاتی‌تر:** تلفنچی حتی برای این خطای ۴۰۰، هدر HTTP را `200 OK` می‌فرستد (خطای واقعی فقط داخل بدنه‌ی JSON است)! کد ما فقط httpCode transport را چک می‌کرد (که همیشه ۲۰۰ بود)، پس خطای واقعی همیشه «موفق» تشخیص داده می‌شد. رفع شد: تشخیص موفقیت الان فقط بر اساس `status==="Ok" && code===200` از بدنه‌ی JSON است. همچنین بررسی توکن webhook از حالت مسدودکننده (403) به لاگ‌کننده‌ی غیرمسدودکننده تغییر کرد چون در تست واقعی، رویدادهای واقعی هم رد می‌شدند (علت دقیقش هنوز در حال بررسی است). |
| نسخه ۱۰ (فعلی) | **باگ بنیادی «تماس ورودی هیچ‌وقت سرنخ نمی‌گیرد» پیدا و رفع شد:** ساخت خودکار سرنخ فقط در `ingestRingingEvent()` انجام می‌شد (نگاه کنید به «راهنمای سریع» پایین همین فایل) - رویداد `ringing` تضمینی برای رسیدن ندارد و ممکن است دیرتر از `hangup` برسد یا کلاً از دست برود. تنها شبکه‌ی ایمنی باقی‌مانده (`Call::autoGenerateLeadsFromRecentCalls()` در `runSync()`) فقط وقتی `$newCount > 0` اجرا می‌شد؛ اما چون وب‌هوک تقریباً همیشه زودتر از sync دوره‌ای تماس را در `calls` درج می‌کند، `$newCount` تقریباً همیشه صفر بود، پس این شبکه‌ی ایمنی در عملیات روزمره عملاً هیچ‌وقت اجرا نمی‌شد. رفع شد: (۱) `autoGenerateLeadsFromRecentCalls()` حالا در هر اجرای sync بدون قید صدا زده می‌شود، (۲) `processCall()` (که هم از `ingestHangupEvent` و هم از `runSync` استفاده می‌شود) هم حالا به‌عنوان لایه‌ی دوم مستقل تلاش می‌کند سرنخ بسازد، (۳) خطاهای این مسیرها حالا در `telefonchy_api_logs` هم لاگ می‌شوند (نه فقط فایل لاگ سرور). |\n| نسخه ۹ | **باگ نهایی و اصلی با یک curl موفق (سورت درست) کشف و رفع شد:** ساختار پاسخ واقعی یک لایه‌ی تودرتوی مستندنشده دارد - لیست تماس‌ها در `data.data` است نه `data.calls`، و صفحه‌بندی در `data.pagination` است نه `paginator`. کد قبلی چون این کلیدها را پیدا نمی‌کرد، کل آبجکت پاسخ (شامل `status`, `pagination`, ...) را به‌جای لیست تماس واقعی fallback می‌گرفت و بی‌صدا هیچ تماسی ذخیره نمی‌شد. همچنین مشخص شد که بدون فیلتر تاریخ، تلفنچی پیش‌فرض را روی «فقط امروز» می‌گذارد (نه کل تاریخچه)؛ گزینه‌ی «همه‌ی تاریخچه» حالا صریحاً از سال ۱۳۹۴ شروع می‌کند. |

## چک‌لیست عیب‌یابی با curl (وقتی نتیجه‌ی sync عجیب بود)

قبل از تغییر هر کدی، این را مستقیم در ترمینال اجرا کنید (نه از داخل
برنامه) تا مطمئن شوید مشکل از تلفنچی است یا از کد ما:

```bash
# در ویندوز اگر پراکسی/VPN سیستمی دارید، اول این را بزنید:
set HTTP_PROXY=
set HTTPS_PROXY=

curl -i -H "webservice-token: {TOKEN}" "https://panel.telefonchy.com/webservice/v1/calls?service_id={SERVICE_ID}&page=1&sort=created_at%20DESC"
```

نکته: `sort=created_at DESC` باید URL-encode شود (`created_at%20DESC`)
چون فاصله دارد؛ curl گاهی خودش این کار را می‌کند اگر داخل `""` بگذارید.

پاسخ را طبق جدول کد ۰ همین فایل تفسیر کنید: اگر `"code":400` دیدید،
حتماً به پیام `message` نگاه کنید - معمولاً می‌گوید دقیقاً کدام پارامتر
اشتباه است (همین‌طور مشکل `sort` کشف شد).

## اگر بازم «۲۰۰ موفق ولی صفر تماس» دیدید

با نسخه‌ی فعلی، لاگ موفق هم خلاصه‌ی پاسخ واقعی تلفنچی را نشان می‌دهد (نه
فقط برای خطاها). بعد از تلاش دوباره، به لاگ نگاه کنید:
- اگر نوشته `data: null (تلفنچی می‌گوید هیچ نتیجه‌ای نیست)` → یعنی
  واقعاً از نگاه تلفنچی، با این `service_id` و این بازه، تماسی نیست
  (احتمالاً چند سرویس/خط دارید و `service_id` ذخیره‌شده مال خط دیگری است -
  از «تست اتصال» دوباره لیست سرویس‌ها را چک کنید).
- اگر عددی مثل `47 آیتم در پاسخ` نشان داد ولی باز هم در دیتابیس محلی
  ذخیره نشد → مشکل در پردازش (`CallSyncManager::processCall`) است، نه
  در ارتباط با تلفنچی؛ همان لاگ خطای «پردازش تماس» را بفرستید.

## راهنمای سریع فیچرهای جدید نسخه ۶

### تبدیل تماس به سرنخ (Lead)
- در لیست تماس‌ها یا صفحه‌ی جزئیات تماس، دکمه‌ی «➕🎯 تبدیل به سرنخ» فقط
  وقتی نمایش داده می‌شود که تماس شماره‌ی معتبر داشته باشد و قبلاً تبدیل
  نشده باشد.
- شماره‌ی مشتری بر اساس نوع تماس تعیین می‌شود: ورودی → `call_source`،
  خروجی → `call_dest`.
- سرنخ ساخته‌شده در جدول `leads` با `source: 'تلفنچی'` و یادداشتی شامل
  جزئیات تماس (نوع، وضعیت، مدت، تاریخ) ثبت می‌شود؛ `calls.lead_id` هم
  برای جلوگیری از تبدیل تکراری به‌روزرسانی می‌شود.
- پیاده‌سازی: `Call::convertToLead()`, `POST /api/calls/{id}/convert-to-lead`

### اتصال داخلی‌ها به پرسنل (اپراتورها)
- تنظیمات → پنل «🔗 اتصال داخلی‌ها به پرسنل» → برای هر داخلی دیده‌شده در
  تماس‌ها، یک نفر از پرسنل را از dropdown انتخاب و «ذخیره» کنید.
- این کار مقدار `staff.exten_number` را ست می‌کند (از طریق
  `PUT /api/staff/{id}`). بعد از آن، در لیست و جزئیات تماس، به‌جای شماره‌ی
  خام داخلی، نام همان پرسنل (لینک‌شده به پروفایلش) نمایش داده می‌شود.
- برای قطع اتصال یک داخلی از یک نفر، فعلاً باید از پروفایل خودِ آن پرسنل
  فیلد داخلی را خالی کنید (حذف مستقیم از این پنل هنوز اضافه نشده).

### همگام‌سازی بازه‌ی تاریخ دلخواه
- دکمه‌ی معمولی «🔄 همگام‌سازی» فقط از `last_sync_at` ثبت‌شده تا الان را
  می‌گیرد (برای استفاده‌ی روزانه/افزایشی).
- برای گرفتن تاریخچه‌ی قدیمی‌تر (backfill)، ابتدا فیلترهای «از تاریخ» و
  «تا تاریخ» پایین صفحه‌ی تماس‌ها را پر کنید، سپس روی «📅 همگام‌سازی
  بازه‌ی انتخاب‌شده» بزنید.

## تحلیل هوشمند تماس (AI Analysis) - اضافه‌شده در همین نسخه

📖 منبع: صفحه‌ی رسمی راهنمای تلفنچی «تحلیل هوشمند تماس» (help/api/call-ai-analysis)،
تاریخ سند: ۱۹ شهریور ۱۴۰۵ - متن کامل توسط کارفرما ارسال و مستقیم پیاده‌سازی شد.

### ⚠️ نکته‌ی مهم: این endpoint قرارداد پاسخ متفاوتی دارد
برخلاف بقیه‌ی این کلاینت (`getCalls`, `getCallInfo`, ...) که پوشش
`{status:"Ok", code:200, data:...}` دارند، این دو endpoint موفقیت/وضعیت
را از روی **خودِ کد HTTP واقعی** مشخص می‌کنند:
- `POST /calls/analysis/request`: `200` = قبلاً کامل شده (رایگان این‌بار)،
  `202` = تازه ثبت شد یا در حال پردازش است.
- `GET /calls/analysis/show`: همیشه `200`؛ وضعیت واقعی در فیلد
  `analysis_status` بدنه است.
- خطاها: `400` ورودی/حساب نامعتبر، `401` توکن/IP/سهمیه، `402` ماژول یا
  صوت مناسب در دسترس نیست، `404` یافت نشد، `429` سقف Polling (به همراه
  هدر `Retry-After`)، `500` خطای داخلی.

به همین دلیل پیاده‌سازی این دو متد (`requestCallAnalysis`, `getCallAnalysis`)
از متد عمومی `request()` استفاده نمی‌کند، بلکه یک پیاده‌سازی curl مستقل
(`analysisRequest()`) دارد.

### جریان کار
1. `POST /api/calls/{id}/analysis/request` (سمت جاکجاست) → پیدا کردن
   `cuid` تماس از دیتابیس محلی → `POST /calls/analysis/request` به تلفنچی
   با بدنه‌ی JSON `{service_id, cuid}` (بدون `record_id` - طبق مستندات
   خودِ تلفنچی از `cuid` استخراج می‌شود) → ذخیره‌ی نتیجه در ستون‌های جدید
   `calls.ai_analysis*`.
2. فرانت (`call_detail.php`) هر ۴ ثانیه `GET /api/calls/{id}/analysis`
   می‌زند (که خودش هر بار هم یک‌بار از تلفنچی poll می‌کند و در دیتابیس
   به‌روزرسانی می‌کند) تا `ai_analysis_status` به `completed`/`failed` برسد.
   این GET سمت تلفنچی رایگان است (از `remains` کم نمی‌کند).
3. در لود اولیه‌ی صفحه هم یک‌بار `GET .../analysis` زده می‌شود (بدون
   ارسال درخواست جدید) تا اگر قبلاً تحلیلی درخواست شده، بدون هزینه‌ی
   اضافه نمایش داده شود.

### ستون‌های جدید جدول `calls` (auto-migration، نیاز به SQL دستی نیست)
`ai_analysis_status`, `ai_analysis_progress`, `ai_analysis` (JSON کامل
پاسخ تلفنچی)، `ai_analysis_requested_at`, `ai_analysis_updated_at`.

### پیاده‌سازی
- `TelefonchyAPI::requestCallAnalysis($cuid)`, `TelefonchyAPI::getCallAnalysis($cuid)`
- `Call::saveAiAnalysis()`, `Call::getAiAnalysis()`
- `POST /api/calls/{id}/analysis/request`, `GET /api/calls/{id}/analysis`
- نمایش: پنل «🤖 تحلیل هوشمند تماس» در `views/call_detail.php` (خلاصه،
  نتیجه، پیشنهاد به اپراتور، احساس مشتری، کلیدواژه‌ها، گزارش کامل، و متن
  تفکیک‌شده‌ی اپراتور/مشتری فقط وقتی `transcript_by_role.mapping === 'verified'`)
